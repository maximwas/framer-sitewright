Get started

Sitewright docs

Sitewright is an MCP server that lets AI agents — Claude Code, Cursor, Codex — build and edit Framer sites: design tokens and text styles, pages and sections, breakpoints, components, images, CMS content and translations. It runs on your computer, works in the Framer project you have open, and records every change in a journal you can undo.

Unofficial. Sitewright is not affiliated with or endorsed by Framer. “Framer” is a trademark of Framer B.V. It is free and open source under the MIT license.

You need:

  • Node.js 24.11 or newer on macOS, Linux or Windows.
  • An MCP client: Claude Code, Cursor, Codex or any agent that speaks MCP.
  • A Framer project you can edit, and the Sitewright plugin in it.
  • Optionally, the project's Server API key. Without one, the plugin does the work; a key adds effects, components, rich text, screenshots and catalogs (see Working without a key).

Install

Run the setup wizard in a terminal:

npx -y sitewright@latest

It asks, step by step:

  1. which clients to connect: Claude Code, Cursor, Codex;
  2. the Server API keys of your projects, one per project (you can skip it and add them later);
  3. what the agent may do: custom code, code components;
  4. whether to add the Claude Code hooks that show the skills Claude uses in the journal.

To set it up by hand instead, add the server to Claude Code:

claude mcp add sitewright -- npx -y sitewright@latest

For Cursor, Codex and other clients, add this to their MCP config:

{
  "mcpServers": {
    "sitewright": {
      "command": "npx",
      "args": ["-y", "sitewright@latest"]
    }
  }
}

npx -y sitewright@latest setup --print prints these commands and blocks, for scripts. After a Sitewright update, reconnect the server in your client (in Claude Code: /mcp → reconnect) so it sees the new tools.

Connect the plugin

  1. Open your project in Framer, then Plugins → Sitewright.
  2. Click Connect. A small window opens: the journal. It carries the plugin's connection to Sitewright, so keep it open while you work.
  3. The plugin says Connected. Ask your agent to start with project_overview.

Sitewright works in the project the plugin is open in. Open the plugin in another project and the agent follows it; nothing runs while no plugin is connected, so a change never lands in a project you did not open.

Browsers do not let a published plugin talk to your computer directly, so the journal window relays for it. If the plugin keeps waiting, check that the window is open and that your agent is running with Sitewright connected.

Server API keys

A key gives Sitewright Framer's Server API for one project, including Framer's agent layer (its layout language). Create one in Framer: Site Settings → General → API Keys. Then save it: 

npx -y sitewright@latest key          # add a project's key
npx -y sitewright@latest key list     # the projects with a key
npx -y sitewright@latest key remove   # remove one

You can also add it on the journal page: the gear → Server API key. Keys are checked when you save them and stay in ~/.sitewright/keys.json, readable only by you. Sitewright uses the key of the project the plugin is open in; to work on another saved project, name it to your agent (it calls framer_connect).

Guide

How calls reach Framer

Every call goes one of three ways, and the journal tags each entry with the one it took:

Path Needs Used for
Plugin API The plugin, connected Everything it can do, first: changes land live in the editor.
Server API The project's key Screenshots, catalogs, large uploads, reads the plugin cannot make.
Framer agent The project's key Framer's layout language: effects, variants, components, rich text, shadows.

The default mode, auto, needs the plugin connected. SITEWRIGHT_TRANSPORT=server-api is the mode for working without the editor open, on purpose: the agent then works on the saved project you name.

Working without a key

With the plugin alone, the agent can:

  • build pages from frames and text: layout (stacks, grids), sizes, positions, fills, borders, radius, links;
  • fill frames with a color, a token, a linear gradient or an image from a URL;
  • manage color tokens and text styles, including sizes per breakpoint;
  • add Tablet and Phone breakpoints and adapt their copies;
  • add SVG, upload images and files, set component controls;
  • edit CMS collections, fields and items, and write translations;
  • write code files and custom code, when you allow it.

These need a key: effects and motion (hover, appear, scroll), variants and components, rich text, text color on a text node (put it on the text style instead), shadows, radial and conic gradients, screenshots, the icon, component and stock photo catalogs, and deleting a whole CMS collection. A batch that asks for one of them changes nothing and says what needs the key.

The journal and undo

Every call is an entry: what the agent read or changed, how it reached Framer, and what it touched — tokens, styles and layers you can click to select in the editor. Open the journal page with sitewright open, the plugin's Open journal, or ask the agent (activity_open).

  • All · Changes · Reads · Skills pick what the list shows.
  • Undo takes back the newest change; Undo on an entry takes back that change and everything after it.
  • Redo puts back what the last undo took.
  • Mark sets a checkpoint, and Restore beside it undoes everything since, with a preview first.
  • Clear starts the journal over: the changes stay in Framer, but can no longer be undone from here.

What you undo on the page, the agent hears about with its next result, so it re-reads before building on it. Edits you made yourself after the agent are kept: undo skips them unless you choose to revert them too.

Not undoable yet: CMS changes, translations, component controls and deleted code files. Those tools say so, and a deletion returns what it removed, so the agent can put it back.

What the agent may do

Switches on the journal page (the gear) or in the terminal (sitewright settings, sitewright settings customCode=on). Every agent session follows them.

Switch What it does
Plugin first While the plugin is connected, the agent works through it, so changes land live in the editor. Only what needs Framer's layout language, screenshots and catalogs go through the Server API. Off: the Server API does everything it can.
Custom code Lets the agent add HTML to every page: analytics, verification tags, embeds. Off: it tells you what needs code instead of writing it.
Code components Lets the agent write React code components and overrides for what the canvas cannot do. Off: it builds with canvas components, variants and effects only.
Support reminders At most once a week, after a change, the agent mentions how to support Sitewright. Off: never.

Design guide and layout audit

design_guide gives the agent the order of work, layout and type rules, direction measured on top Framer sites, the habits of generated pages to avoid, and the checklist before a page is handed over. The Claude Code skill (sitewright setup --skill) points the agent at it.

After every design_apply, Sitewright audits what the batch touched, and layout_audit checks a whole page with its breakpoints. The audit looks for what breaks on the published site: children on different edges, cards of uneven height, text links in the default blue, sections wider than the rest, fixed sizes that break on phones, grids too dense for a phone, missing headings, uneven spacing.

Pages as XML

nodes_read returns a page or a layer as XML: one tag per layer with its attributes. design_apply takes the same XML back:

  • a tag with an id changes that layer, only in the attributes it gives;
  • a tag without one creates a layer, inside the tag around it or in the parent it names;
  • $delete="true" removes the layer;
  • a key names a new layer: its id comes back in the result, and a later tag's parent can use the key;
  • with a key, raw DSL works too (dsl: moves, duplicates, variants).
<FrameNode id="hero" gap="24px">
  <RichTextNode key="title">Build calm spaces</RichTextNode>
  <FrameNode id="old-banner" $delete="true" />
</FrameNode>

Skills in the journal

Claude Code loads skills itself, so Sitewright learns about them through Claude Code hooks. With them on, the journal shows which skills Claude used for a change. 

npx -y sitewright@latest setup --hooks          # print the hooks to add
npx -y sitewright@latest setup --hooks --yes    # add them (a .bak copy of your settings is kept)

Restart Claude Code afterwards.

Configuration

Set these in the environment of the MCP server, in your client's config.

Variable Default What
SITEWRIGHT_TRANSPORTautoauto (through the plugin, nothing without it), server-api or plugin.
SITEWRIGHT_HOME~/.sitewrightThe journal, keys, settings, logs and the bridge's port.
SITEWRIGHT_BRIDGE_PORT18710The journal page and the plugin's bridge.
SITEWRIGHT_PLUGIN_BRIDGEonoff: no bridge for the plugin.

LOG_LEVELinfoLogs go to stderr and to ~/.sitewright/logs/.

Files on your computer

Everything stays in ~/.sitewright; nothing goes anywhere but Framer.

  • keys.json — the Server API keys, one per project, readable only by you;
  • settings.json — the switches;
  • the journal of each project, which undo reads;
  • logs/ — the logs (sitewright logs);
  • bridge.json — the port the journal page and the plugin's bridge use.

There is no telemetry and no account.

Troubleshooting

“The Sitewright plugin is not connected”
Open the plugin in your project, click Connect, and keep the journal window open. Without the plugin nothing runs, unless you chose SITEWRIGHT_TRANSPORT=server-api.
The plugin keeps waiting
The journal window looks for the MCP server your agent runs. Start your agent with Sitewright connected (in Claude Code, /mcp); the window reconnects by itself.
The agent does not see a new tool
Reconnect the server in your client after an update (in Claude Code: /mcp → reconnect).
A change needs a key
The result names what needs the Server API. Add the project's key with sitewright key or on the journal page, or ask the agent for the way that works without one.
Something else
sitewright logs follows what every running server does. Issues and questions: GitHub.

Tools

All tools

Every tool as your agent sees it: what it does, its parameters, whether it only reads, and what it needs. You rarely call them yourself: you ask, and the agent picks them.

  • Reads never changes the project
  • Changes changes it, with undo unless the tool says otherwise

Shows the active transport (Server API or the Framer plugin), whether each one is configured and connected, what to do if not, the projects with a saved Server API key (framer_connect { project } switches between them), and what the project's Framer plan allows. Call it when a Framer tool fails.

framer_connect

Changes Local

Choose Framer transport or project

Switches how tools reach Framer, which project they edit, or both. transport: "server-api" (API key, headless, DSL + screenshots), "plugin" (the Sitewright plugin open in the editor; Plugin API only) or "auto" (everything through the connected plugin, the DSL through the Server API of its project; nothing runs while the plugin is not connected). project: when the user names another project, switch to it here, by name from framer_status's projects (only those have a saved key); the plugin follows only if it is open in that project. Returns the new status.

ParameterTypeWhat

projectstring | nullA project with a saved Server API key, by name, id or editor link: the Server API switches to it, also without the plugin, until the plugin is opened in another project. null: follow the plugin's project again. Leave out to keep the current one.
reconnectbooleanReopen the Server API session first. It keeps the project as it was when it connected, so after people change things in the editor (vector sets, uploaded fonts, edits) reconnect to see them. default false

fonts_discover

Reads Local

Discover fonts

Finds fonts beyond Framer's library search, in Google Fonts and Fontshare: by words of the name, category (sans, serif, display, slab, mono, handwriting) and order (popular, trending, new). Each comes with its license in plain words, its weights, a specimen link, and whether Framer's library has it (inFramer). Fontshare's license (ITF FFL v2.0) allows uploading its files only to the user's own site: for a client's site or a sold template use a family with inFramer true from Framer's library.

nodes_read

Reads Plugin · more with a key

Read nodes

Reads a node (or the page root) with its children to a given depth, as XML by default: tags are node types, attributes are ids, names and DSL attributes, $-attributes are read-only metadata. Blocks and runs of a rich text show no id: theirs follow from position (v:<text id>:<n>, then :<m>). Edit the XML and send it back with design_apply xml. format "json" returns raw serialize(). Keep depth low and filter attributes on big pages. Without a Server API key it reads through the Plugin API: the same XML with fewer attributes, and the plain text of a rich text instead of blocks and runs.

ParameterTypeWhat
nodeIdstringNode id. Omit to read the page root of pagePath.
pagePathstringPage path, e.g. "/" or "/about". default "/"
depthnumberHow many child levels to include. default 2
attributesstring[]Only these attributes, e.g. ["fill", "layout", "$rect"]. [] returns structure only.
format"xml" | "json"xml: the tree as elements (compact, writable back with design_apply); json: raw serialize(). default "xml"

ParameterTypeWhat

design_apply

Destructive Plugin · more with a key

Apply design changes

Changes a page and returns Framer's diagnostics (errors, warnings, lint, renamedIds). Prefer xml; dsl (raw +Node/SET/DEL/MOVE/DUPE commands) runs after it, for moves and duplicates. Without a Server API key it runs through the Plugin API: xml only, frames and plain text with layout, size, position, fill, radius, border, link and textStylePreset (design_guide dsl lists them), and overrides on breakpoint copies by compound id; anything else refuses the whole batch before a change. XML: tags are node types, attributes are DSL attributes (framer_docs), every value in quotes. An element without id is created: nested ones under their parent element, a top-level one under parent="<id>", at the end unless index="<n>" is given; key="hero" returns its real id in keys, and @hero in any value (scope, component, parent, var(--variable-@label), and the dsl part) points at it within the batch. An element with id gets a SET of only the attributes it lists; $delete="true" deletes it. Nesting existing nodes only addresses them: nothing moves and omitted children stay. Inside an existing rich text, blocks and runs without id are the ones at that position (as nodes_read prints them); give a new one a key. Text: plain text inside a RichTextNode, or <TextBlock tag="h1">…</TextBlock> blocks with <TextRun bold="true">…</TextRun> runs; write & and < as &amp; and &lt;. Nested attributes are dotted: hoverEffect.scale="1". With a key, color text with a token on the RichTextNode itself, textColor="var(--token-<id>)", not only through its text style: only then does the token show in Framer's Color field. Framer applies every command it can and skips the failed ones: send only the failed commands again, fixed, never the whole batch (it would create its nodes twice). Pass pagePath for a node that is not on the home page (nodes_find and selection_get give it). Read design_guide dsl before the first batch.

ParameterTypeWhat
xmlstringNodes as XML, e.g. <FrameNode parent="<id>" key="hero" layout="stack"><RichTextNode>Hi</RichTextNode></FrameNode>. Without id: created (key names it in the answer); with id: SET of the attributes given; $delete="true" deletes.
dslstringFramer DSL commands, each ending with ";", applied after the XML. See framer_docs "Updating the Project".
pagePathstringPage the commands apply to. default "/"

effects_set

Changes Server API key

Set motion effects

Puts a motion preset on layers in one call: every value of the effect is written (Framer fills in its own otherwise: a hover scale of 1.1, a loop that spins, a scroll transform at half opacity), transitions are springs without bounce of the kind Framer keeps there, and delays grow along nodeIds. Prefer it to writing effect attributes with design_apply. Presets: fade-up (cards and blocks below the fold appear on scroll, one after another); hero-sequence (the first screen's heading, text and media appear on load, 0.1s apart); text-reveal (a heading appears word by word as it enters); hover-lift (a card or button rises 4px on hover); hover-fade (a link or image dims slightly on hover); press (a button gives way to 97% when pressed); float (a badge or illustration drifts up and down); pulse (a dot or badge breathes in scale); spin (a badge or mark turns slowly); scroll-grow (an image or section grows from 86% as it scrolls in); parallax (an image moves against the scroll inside a clipped frame (put it on the inner layer)); ticker (a stack of logos or words runs as a marquee, slower on hover); remove (removes the effects named in options.effects (all of them without it)). Hover and press go on a plain layer or a layer inside a component, never on a variant or breakpoint root (Framer refuses there). Effects never run on the canvas or in screenshots: say so and check them in Preview. Undo takes a preset back. Needs the project's Server API key.

ParameterTypeWhat
preset"fade-up" | "hero-sequence" | "text-reveal" | "hover-lift" | "hover-fade" | "press" | "float" | "pulse" | "spin" | "scroll-grow" | "parallax" | "ticker" | "remove"The effect to put on the layers. required
nodeIdsstring[]The layers, in the order they should move (delays grow along this list). required
pagePathstringThe page the layers are on. default "/"
optionsobject default {}
  • delay number optional — Seconds before the first layer starts.
  • stagger number optional — Seconds between layers in order.
  • distance number optional — Pixels of travel.
  • duration number optional — Seconds the spring takes.
  • effects "appearEffect" | "hoverEffect" | "tapEffect" | "loopEffect" | "styleTransformEffect" | "textEffect" | "tickerEffect" | "parallaxEffect" | "scrollVariantEffect"[] optional — For "remove": which effects to take off; all of them when omitted.

layout_audit
